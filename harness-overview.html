Autonomous research, explained

How the crux harness lets one AI agent write a research paper on its own

Give it a research question, about a week, and a compute budget. Then leave. This page shows the moving parts that keep a fully autonomous agent honest, on-target, and productive — from the files it lives in to the mechanical gates that decide when it's allowed to ship.

The big idea

crux is an autonomous research agent built on the OpenClaw runtime. A human operator hands it a brief and walks away. The agent plans the project, reads the literature deeply, runs its own GPU experiments, writes the paper, sends it to external reviewers, and reports back — deliberating before each move and making every decision itself. The operator is an observer, not a collaborator: the agent sends routine one-way status updates, but only two messages may ever ask anything of them.

The whole design exists to answer one question: can an agent do a real, week-long research project without supervision — and what does it need so that "no supervision" doesn't become "no rigor"? The design leans on a small set of rules and strong heuristics: an agent that deliberates, a compute budget framed as a target to deploy on depth (not just a ceiling), and a handful of isolated critics whose verdicts the agent honors cooperatively.

A run, from start to finish

A run is a research cycle, not a one-way staircase: Set up → Explore ⇄ Experiment ⇄ Draft ⇄ Review → Presentation Overhaul → Ship. The ⇄ back-edges are normal research — returning from Draft or Review to run another experiment is exactly what a good researcher does, not a failure or a pivot. Exploration still comes first and gets a big share of the clock — roughly 30–40% of the horizon, whatever its length (a deep read of the literature, plus scouting experiments); drafting in earnest waits until an isolated critic agrees the evidence is real.

  1. 1

    Set up

    Verify the environment; build an empty paper that already compiles in the venue template; write the research-plan spine and a costed budget-deployment menu.

    gate: skeleton builds
  2. 2

    Explore

    Survey the literature with citation-graph APIs (forward/backward walks, not just web search), then deep-read the 3–5 closest papers in full (methods + results), and scout 2–3 candidate approaches with real experiments.

    authorized by: exploration critic (who can search the literature itself)
  3. 3

    Experiment

    Run the most decisive experiments at depth — more seeds, more scale — spending the budget on evidence before polish.

    ⇄ revisited from Draft / Review
  4. 4

    Draft

    Commit to a headline after scouting and write the paper. A real finding sends you back to Experiment — the default fix is "what experiment closes this?", not "narrow the claim."

    ⇄ back to Experiment is normal
  5. 5

    Review

    Hostile internal reviews, then isolated blind rounds and real external reviewers, fixing soundness issues each round until a round adds nothing new.

    ⇄ back to Experiment is normal
  6. 6

    Presentation Overhaul

    A mandatory rewrite for cold-reader legibility: restructuring is authorized, the claims and numbers are frozen. Exit only by acceptance test — mechanical gates plus two fresh cold-readers — never by self-judgment.

    gate: REQUIRE_PRESENTATION + 2 cold-readers

…then Ship: the camera-ready paper plus an honest final review — and, as the run's very last commit, a plain-language README that lets a visitor with zero context understand the repo, find the paper, and reproduce the headline result.

Success bar: the paper reaches a peer-review score of Weak Accept or higher. Reviewers are isolated and their verdicts can't be authored by the agent, so the only way to pass is to genuinely earn it. Falling short — or finishing with most of the budget unspent — while time and budget remain is treated as a failure to fix, not a finish.

Under the hood: how OpenClaw runs the scaffold

Two things work together. OpenClaw is the runtime engine — it wakes the agent on a schedule, runs each turn through the model, spawns isolated helper agents, and executes tools. The workspace scaffold is the set of plain Markdown/JSON files that steer that engine toward a rigorous paper. The figure shows both layers and how a turn flows through them; the pieces marked with a dot () are engineered specifically for this research task.

Read the diagram as text — how a single turn actually runs
  1. Wake. A heartbeat cron (or a self-scheduled harvest cron) wakes the main session. The agent reads the day's short state capsule in memory/ and the tail of LOG.md to recover context — it starts each turn fresh, so the files are its memory.
  2. Act. It takes exactly one forward action — the End-of-Turn Contract: launch a background job, delegate to subagents, log a decision memo and act on it, pass a milestone gate, or sit tight on a sufficient experiment that is still running (the Mature state). The only banned ending is waiting on a human or leaving a decision unmade.
  3. Delegate / experiment. Real work goes to isolated subagents (deep literature reads, section drafts, and the unauthorable review/critic subagents) or to GPU jobs on RunPod — each launched with a pre-registered "if it passes/fails, do X" branch protocol and a scheduled harvest cron.
  4. Harvest & record. When a job finishes, a cron wakes the session to read the result file, spot-check a surprising or claim-bearing number against the artifact it claims, and write the outcome into PLAN.md, LOG.md, and — for a pre-registered falsifier or a headline-claim change — the light REGISTRY.md.
  5. Gate. At each milestone the agent runs scripts/gate_artifact.sh. The form/hygiene checks are always on; the ship-time checks read an isolated critic's own artifact (reviews/power_critic_ship.md, reviews/final_review.md) and the budget lock in locks/ directly — never an agent-typed string — and exit GATE FAIL if a rule isn't met. The agent honors a failing gate.
  6. Enforce (optional ship-time backstop). If the enforcement plugin is installed, OpenClaw's typed hooks turn the ship gates into runtime vetoes — a failing ship gate blocks the turn or cancels the completion message — so the one irreversible action can't be skipped. Everything earlier stays cooperative.
  7. Report. Scheduled snapshots and (once) the completion report go to the operator over Telegram; external reviews return via Gmail/API and re-enter the loop at step 4.

The workspace: the agent's brain on disk

The agent "wakes up fresh" each turn — its memory is a set of plain Markdown files. Some are rules it must follow, some are working memory it keeps current, and some are the ground truth about its tools and frozen definitions.

Task & rules — what it must do and how

BRIEF.md

The research question, the success bar, the budgets, and the "must / must-not" constraints.

AGENTS.md

The operating constitution: the research question and success bar up top (so even subagents know the goal they serve), how every turn must end, the decision tiers, and the evidence rules.

HEARTBEAT.md

A periodic "sweeper" that harvests finished jobs, watches the clock, and checks spend.

USER.md

The operator contract: one-way status updates and the only two messages that may ask for anything.

Working memory — kept current as the run unfolds

PLAN.md

The living plan: the research-plan spine, candidate portfolio, milestone table, and work queue.

REGISTRY.md

A light pre-registration surface: falsifiers declared before their experiment, a locks index, and a short claim & decision trail. Not an append-only contract.

LOG.md

The decision trail — every significant choice written as a memo before acting on it.

memory/

A short daily "state capsule" so a restarted agent instantly knows where things stand.

Procedures & ground truth

playbooks/

Step-by-step procedures for decisions, exploration, review, writing, figures, and subagents.

TOOLS.md

Environment truth: GPU cloud, email, reviewer platforms, literature-search APIs (citation walks as single calls), and hard-won "footguns" to avoid.

locks/

Frozen definitions as JSON (budgets, evidence floors) that code reads so they can't quietly drift.

scripts/

The mechanical checkers: the gate script and the spend meter. Numbers are measured, never guessed.

How it makes decisions without anyone to ask

With no human to consult, the harness replaces "ask for approval" with discipline: every turn must produce forward motion, and every meaningful choice is a logged, reversible decision rather than a pause.

Every turn ends in one of five states

What's banned is narrow: waiting on a human, an unmade decision, and churning out small work just to look busy. Letting a sufficient experiment run is forward motion.

  • ①
    Launch — a background job is running, with a pre-registered plan for each possible outcome and a scheduled check-in.
  • ②
    Delegate — one or more isolated subagents are working, each with a deadline and a deliverable.
  • ③
    Memo — a decision is written down and its first action taken — never "decide later."
  • ④
    Milestone — a gate passed; the milestone is marked done and the next one's first action begins.
  • ⑤
    Mature — a sufficient experiment or job is already running; the right move is to let it finish, or to deepen it (more seeds, more scale), not to launch a small new thing to avoid an idle turn.

Three tiers of decision authority

The operator is never a gatekeeper. Almost everything is the agent's to decide and record.

  • T1
    Act & log — anything inside scope: methods, experiments, tooling, spend within budget.
  • T2
    Logged memo — choices that change the contribution: write the memo, run critic subagents, then proceed on a branch.
  • T3
    Blocking contact — only two triggers: a broken external tool it can't route around, or the final completion report.
When a finding lands — and when an approach actually dies

The default response to a real review finding is "what experiment closes this?" — going back to Experiment is normal research, not a pivot. Narrowing the claim is the fallback, used only when the closing experiment is genuinely out of budget. A costed-but-unrun lever — a larger-model arm, an un-run robustness experiment — is forward motion the run owes, never "grinding" to be declined.

The stuck tripwire fires only on repetition of a tried-and-failed approach. When it does, the agent diagnoses what broke before reacting: a code/setup problem (fix it), a mechanism problem — the idea's premise is wrong (advance the next candidate in the portfolio), or a question problem — the whole portfolio is exhausted (re-scope, but only after the alternatives have genuinely been tried). Polishing the writing or narrowing the claim does not count as clearing a real rejection.

How it stays honest — and good

An unsupervised agent's biggest risks are making things up and over-claiming. The harness answers both with a small set of evidence heuristics the agent applies — and a layered review pipeline of isolated critics it cannot talk around, whose written verdicts it honors cooperatively. A small set of rules, applied with judgment, does the work of a long checklist.

Three evidence heuristics (these bind subagents too)

  • 📎
    Artifact or it didn't happen. Every load-bearing number names the file it came from; a number with no artifact is treated as fabricated. Re-derive it once, when first promoted to a claim — not every round.
  • ⚖️
    Both sides of every headline. A success metric must ship with its cost / false-alarm metric — never the win alone.
  • ↔️
    Symmetric claim discipline. Over-claiming and hedging below the evidence are equal defects: make the strongest claim the evidence supports, no more and no less.

Plus one kept pre-registration: the falsifier that would kill a claim is declared before its experiment runs. Surprising or claim-bearing subagent results are spot-checked — not every report re-verified.

The success bar is earned, not declared

The paper only "passes" when isolated reviewers — internal and external — score it Weak Accept or higher. Crucially, the agent cannot author those verdicts: review subagents see only the PDF, and external reviews come from real third-party services. There is no way to manufacture the score, so the only path to success is to actually meet the bar — or to ship an honest below-bar result and say so plainly.

The review pipeline

§1

Hostile section reviews while writing — the cheapest way to catch a made-up number.

§1b

Underclaim audit — the counter-force that stops the paper being over-pruned.

§2a

Internal blind rounds — isolated reviewers; stop when a round adds no new soundness finding.

§2b

External reviewers — real third-party services (a required milestone, not an option).

§2c

Accompanying final review — ships with the paper, verdict exactly as written; the gate reads it directly.

§2d

Power critic — is the headline actually supported, or resting on a single data point? Its file is the evidence the ship gate reads.

§3

Brief-fidelity review — does the paper still answer the question that was assigned?

Default response to a real finding: "what experiment closes this?" — go back to Experiment. Narrowing the claim is the fallback when the experiment is genuinely out of budget. A lone favorable review can't overrule same-axis soundness rejections. And fixes may not accrete hedges: a fix whose only edit is a new qualifier sentence is a smell — prefer deletion, restructuring, or a closing experiment. An early single cold-read at the first full draft catches structural legibility problems while the Draft ⇄ Experiment back-edge is still open.

Then the mandatory Presentation Overhaul acceptance-tested

Revision rounds reliably rot prose — each review fix adds a hedge, a qualifier, an internal term; the accumulated result is an over-long abstract, ALL-CAPS emphasis, jargon-saturated sections, and figures that never got built. So once soundness review converges, a mandatory overhaul removes the scar tissue wholesale. Restructuring is authorized (reorganize, rewrite, rebuild figures); the science is frozen — no claim, number, or evidence may change, verified afterward against the claim registry and a brief-fidelity check. Requirements: a 5–6-sentence abstract under a hard word cap, zero ALL-CAPS or internal vocabulary, figures in the main body, a de-hedging sweep, and structure matched to well-written exemplar papers. Exit is an acceptance test, not a self-judgment: the mechanical presentation gates must pass and two fresh cold-readers, given only the PDF, must correctly extract the claim, its evidence standard, and why it matters. Three failed rounds forces a diagnosis memo — the test never softens, and milestone deadlines move before this gate does.

And one last act: the final README. Before the completion report, the agent writes the repo-root README for a visitor with zero context — what the project found (at exactly the registry-licensed strength), where the paper is, a map of the repo, a one-command reproduction, and data provenance — passes its own gate plus a cold-reader, and commits it as the run's final commit. The repo outlives the run; its front door is part of the deliverable.

The gates: a critical few

The harness keeps a deliberate, small set of gates. One checker, gate_artifact.sh, runs at review rounds and milestones. Form & hygiene checks (is this a finished-looking submission?) are always on. The ship-time checks read an isolated critic's own file or the budget lock directly — no self-typed certification string to game — and the presentation & README gates make "accessible" mechanical rather than a vibe.

  • allcaps-proseno ALL-CAPS emphasis in the paper's prose
  • figure-in-bodyat least one figure in the main body — appendix figures don't count
Final README (ship)
  • readme-exists / readme-substantivea real README at repo root, not a stub
  • readme-reproit tells a visitor how to reproduce the headline result
  • readme-vocabularyno internal jargon or ALL-CAPS in the front door

Design principle: the gate reads the evidence an isolated critic already wrote — a power critic's report that says ADEQUATE with its seed/cell counts, the final review's plain-words recommendation, the budget lock cross-checked against live spend. Because there is no agent-typed token in the loop, there is nothing to fabricate: the honesty comes from the unauthorable critic, not from binding strings to disk. The seed/cell floors live in locks/evidence_floors.json; a result thinner than them is an unfinished experiment, not a caveat.

Each guardrail answers a real failure

Nothing here is decorative. Each mechanism exists to catch a specific way an unsupervised agent can fail. A few of the most important:

How common failure modes map to the harness mechanisms that catch them.
If the agent tends to… …the harness catches it with
Escalate to a human, then sit idle waiting The five end-of-turn states — waiting on a human is never a valid ending (the Mature state covers a sufficient experiment still running)
Race to writing on a thin, one-data-point result The evidence-adequacy ship gate reading the isolated power critic's file (§2d), against seed/cell floors
Finish early with most of the budget unspent The felt-budget heuristic (budget is a target to deploy on depth) plus the light ship-authorization backstop
Treat a review finding as a reason to narrow the claim The default response — "what experiment closes this?" — sends the run back to Experiment; narrowing is the budget-exhausted fallback
Over-trust one favorable review and ship below bar The over-index judgment — a lone accept can't overrule same-axis soundness rejections
Quietly answer a different question than assigned The brief-fidelity review (§3)
Skim abstracts instead of reading the key papers The deep-read step + the exploration-sufficiency critic, which checks a full-read note exists per anchor paper before drafting
Invent a statistic that traces to no file The evidence heuristics (artifact or it didn't happen) + hostile §1 section review + spot-checking surprising results
Let revision rounds rot the prose — hedges, jargon, ALL-CAPS, a bloated abstract, no figures The mandatory Presentation Overhaul: mechanical presentation gates + a two-cold-reader acceptance test that cannot be self-judged, with claims frozen while prose is rebuilt
Ship a repo nobody else can navigate The final README stage — a gated, cold-read, plain-language front door committed as the run's last commit
Wedge on a runtime bug overnight and stay dead for hours The box-level session watchdog — detects the failure signature, auto-resets, and the agent resumes from its state capsule (bounded by a cooldown and daily cap)

How strictly are the rules enforced?

The posture is cooperative by default. The agent runs the checks and honors the result; the isolated critics supply the honesty, and the felt budget plus the evidence floor supply the depth. Only the one irreversible action — shipping — is optionally hard-guarded, and there's always a provider-side spend ceiling underneath.

Default

Cooperative gates + isolated critics

The agent runs gate_artifact.sh and honors its exit code, and acts on the critics' written verdicts. A clear GATE FAIL is far harder to talk past than a paragraph of guidance.

Ship backstop

Optional runtime plugin hooks

An optional OpenClaw plugin (hooks/gate-enforcer/) guards ship only: it blocks the ship turn or cancels the "done" message when a ship gate fails, at the runtime boundary. Everything earlier stays cooperative.

Spend cap

Provider spend limit

The runtime has no built-in spend cap, so a hard ceiling is set at the model provider's console as an independent safety net — the only truly hard dollar cap.
