Autonomous research, explained

How the crux harness lets one AI agent write a research paper on its own

Give it a research question, a deadline, and a set of budgets. Then leave. This page shows the moving parts — deliberately few of them — that keep a fully autonomous agent oriented, honest, and productive from launch to the final, accessible write-up.

The big idea: a minimal scaffold

Long-horizon agents don't fail for lack of rules — they fail because rules spread across many files stop binding as context compacts over a multi-day run. So this harness inverts the usual instinct: one standing context file that states the construct, the evaluation, the budget, and every requirement at the top; a self-managed resource budget instead of phase gates; an anchored external check wherever self-assessment is known to drift. Everything else is a heuristic the agent applies with judgment.

A run, start to finish

The shape below is guidance, not gates — the agent owns its schedule through the plan and ledger it writes at hour 0. Moving backward (a review finding sends it back to experiments) is normal research, not failure.

  1. 1

    Set up

    Verify every environment fact against reality; make the paper skeleton compile from the venue template on day 1; write the resource budget and plan.

    gate_artifact.sh live
  2. 2

    Explore

    Read the closest prior work in full — methods and numbers, not abstracts. Test two or three genuinely different approaches on real data before choosing one.

    an early positive = test harder, not stop
  3. 3

    Experiment

    Buy the scale the claim needs — seeds, datasets, baselines — deliberately from the budget. Long jobs run as background processes or GPU pods that write results to disk.

  4. 4

    Draft

    Write from evidence, in the target format, around 1–3 claims stated at exactly the strength the evidence supports. Polish where readers spend attention: abstract, intro, Figure 1.

  5. 5

    Review

    The isolated internal reviewer at every complete draft, then both external reviewers. Verdict-determining issues get experiments, not qualifiers.

    back-edges to Experiment expected
  6. 6

    Final pass

    Auto-dispatched the moment the agent writes its completion report: a presentation-only rewrite, an accessible HTML results page, a cold-visitor README.

    FINAL=1 gate_artifact.sh
  7. 7

    Export

    After the run, from the operator's machine, while the box is still up and before any key is revoked: utils/export-run.sh rebuilds the run log from the session store on the box, scrubs and scans it there, and pulls only the scrubbed outputs into gitignored runs-export/.

    scan-secrets.py on the box

The workspace — everything the agent lives in

Fourteen cards in five groups. The agent's standing context is AGENTS.md alone; the rest are working files it maintains, tools it runs, and — outside the workspace — the operator's messages and the box-side machinery around the run.

Standing context

AGENTS.md

The whole contract in one file: the research question, how the paper will be evaluated and by what standard, the four budgets, the complete numbered requirements list — then the operating reference: delegation, reviews, environment, operator protocol, red lines.

Working files the agent maintains

PLAN.md

The live plan and the resource budget ledger: allocation across phases, spent/remaining per resource, candidate approaches, milestones, work in flight. The restart capsule after any context loss.

LOG.md

Append-only decision trail — every significant decision, result, surprise, and dead end, with artifact paths.

HEARTBEAT.md

The 15-minute beat, triage first: work healthy, nothing finished, ledger fresh, tree clean is an instant HEARTBEAT_OK; any delta earns re-orientation (AGENTS → PLAN → LOG → live jobs), harvest, commit, next action. Reflection belongs to the 6-hour ledger beat, not the heartbeat.

Tools & templates

scripts/gate_artifact.sh

Mechanical form checks before every review round; the extended FINAL=1 set during the final pass.

scripts/telemetry_costs.py · session_costs.py

Scripted API-spend measurement, never hand-estimated. The session store's own per-call usage.cost (deduplicated by responseId) is the ledger — session_costs.py reads it; telemetry_costs.py asks the cost-tracking service for the provider's bill as the external cross-check. Both print $X.XX first; a persistent gap is itself a finding.

templates/paper_template.zip

The venue LaTeX template the skeleton is built from on day 1.

Operator-side (outside the workspace)

PROMPT.md

The launch message: read AGENTS.md, verify the environment, write the budget and plan, begin.

FINAL_PASS.md

The final-stage message, auto-injected by a box-side cron the moment the agent writes its completion report; the operator sends it by hand only as a fallback.

OPERATOR_GUIDE.md

Setup, launch, the operator contract, the post-run export, and the design rationale.

Box-side crons & the export pipeline (outside the workspace)

crux-thinking-watchdog.sh

Every 5 min: if the main session is wedged on cascading invalid-thinking-signature errors, archive the session file, point the registry at a fresh id, restart the gateway, dispatch a recovery turn. Logs under ~/.openclaw/watchdog/.

crux-auth-watchdog.sh

Every 5 min: if the newest N turns all failed for a non-transient reason — revoked key, no permission, exhausted credit — stop the gateway and page the operator over Telegram directly. Dormant while the auth-halt marker exists; the operator fixes the key and removes it, or the watchdog clears it itself once the gateway is back up and an error-free turn has landed. Past the daily halt cap it pages once and leaves the gateway running.

crux-session-snapshot.sh

Every 10 min: keep a current copy of every session-store file — the run record the gateway itself does not preserve (cron transcripts are deleted on the job's next run; a re-keyed main session orphans a generation).

utils/export-run.sh

After the run, from the operator's machine: rebuild the run log from the store on the box, scrub it there with a blacklist that never leaves the box, scan it (counts only), and pull only the scrubbed outputs into gitignored runs-export/. Plugin telemetry rides along as a supplement.

The budget ledger — planning instead of gates

How it works

At hour 0 the agent allocates each resource — hours, API dollars, GPU dollars, OpenRouter dollars — across the phases it foresees: exploration, main experiments, writing, review rounds, the final pass. From then on the ledger is kept continuously current: every meaningful spend, every finished job, every wrong estimate updates it, with measurement always scripted, never estimated. The allocation is freely revisable — a revision is a logged decision, not a failure.

Why a ledger and not gates

Both failure directions are expensive: exhausting a budget early leaves no room to answer reviews with experiments; finishing with most of it unspent means the result is weaker than it could have been. A plan the agent writes and owns keeps both directions visible while there is still time to correct course: a scheduled ledger beat — a cron, every 6 hours — refreshes every budget number and re-judges the direction against the latest results, and the 15-minute heartbeat polices the ledger's freshness in between. Fixed phase gates don't adapt to what the run learns; a living plan does.

Delegation — one unit of work per subagent

The agent delegates self-contained units — a literature survey, an experiment implementation, a section draft, a review — to the framework's native subagents. Because a subagent runs through the gateway, it gets its own transcript in the session store — the record the whole evaluation is analyzed from — so no delegated work is invisible. (The plugin telemetry sees only a subagent's tool calls; its reasoning, text, and final report live in the store.)

Parallelism matched to the phase

Fan out wide on independent work — parallel lit surveys, candidate scouts, ablations — up to the concurrency cap (8); converge to serial when the work is integrative, like drafting one coherent paper, where several isolated writers produce something no reader can follow. One unit of work per subagent; a subagent receives the standing context file plus its brief and nothing else, so everything it needs travels in the brief. Compute-heavy jobs run as background processes, not subagents.

Harvest discipline

Every spawn is recorded in the plan (unit, subagent, deliverable path, ETA). A subagent past its budget, a background job with a silent log, or a GPU pod billing with nothing arriving gets inspected and, if wedged, preempted and re-scoped rather than waited on. Results are harvested from the subagent's report and the on-disk artifact — never from memory of what they should say; before a delegated number enters the paper, the agent opens the artifact it cites.

TASK:        one sentence
SCOPE:       what is in and out; the files it may write
INPUTS:      exact file paths to read
DELIVERABLE: exact output file path(s)
BUDGET:      wall-clock minutes; ship the best 70% if short
EVIDENCE:    per claim, the artifact path + one command that re-verifies it

The review stack — calibrated, isolated, unauthorable

Naively prompted AI reviewers drift lenient and flat: real flaws surface, but buried among minor nitpicks and scored mid-scale. The internal reviewer here is prompt-engineered against both failure modes, and the agent can never author or edit a verdict.

Calibration, by construction

  • 1
    Base-rate anchoring. The reviewer is told the venue accepts ~25% and that the median submission is competent and rejected — competence alone earns nothing.
  • 2
    Verdict-determining issues first, capped at three. The review leads with the 1–3 issues a meta-review would cite if rejecting, each severity-tagged and grounded in a quoted claim — everything else is explicitly “Minor (fix after, never instead of, the issues above)”.
  • 3
    Contribution weighed against flaws. Axes are scored independently (a soundness concern doesn't auto-veto the overall score); only a truly fatal flaw forces a low overall, and the score must reflect the balance of contribution against weaknesses — the reviewer can't narrate acceptance while scoring reject, or vice versa.
  • 4
    Weighted priorities. Data/benchmark motivation and statistical power are judged before novelty and clarity — the issues that actually decide verdicts come first.
  • 5
    Evidence per weakness. Every weakness cites a section/page and a quote; a self-check pass deletes anything unsupported without softening severities.

Isolation, by construction

The reviewer runs as an isolated subagent whose brief hands it only the PDF path and orders it to grade strictly from the manuscript — no round numbers, no prior verdicts, no “we fixed X”. Every round is round one from the reviewer's chair, so the author's framing can never leak into the verdict.

Then two external reviewers

Before completion the agent submits to one portal-based AI reviewer (returned by email, retrieved with the gog CLI) and one API-based paid reviewer, saving every returned review verbatim. Weighing rule: one favorable review never outweighs the others when they flag the same substantive problem.

The gate script — small, mechanical, cooperative

One script, two modes. The agent runs it and honors the exit code; reviewers are never told about it. It checks form — quality is the reviewers' job.

Failure tendency → mechanism

Every mechanism answers a known tendency of long-horizon autonomous research agents. There is deliberately nothing else — where a mechanism can be a heuristic stated once in AGENTS.md, it is.

The operator — mostly absent, by design

During the run

Two one-way snapshots a day: position against plan, what shipped, decisions taken, the resource line, open blockers — never ending in a question. Only two messages may ever ask anything of the operator: a broken external resource the agent couldn't route around, and the completion report. Every unsolicited operator message is an intervention and is logged verbatim on both sides. The box itself pages the operator in exactly one case: the auth watchdog stopped the gateway because the provider rejected every call — a human must supply a key.

At completion — automatic

The moment the agent writes its completion report to the workspace, a box-side cron injects the FINAL_PASS.md message as a user message — no operator in the loop (manual send survives only as a fallback). The agent then cold-reads and restructures the paper (claims frozen), builds the self-contained results.html for a general reader, writes the cold-visitor README, runs the FINAL=1 gates, and sends an updated completion report. Then the run is over.
